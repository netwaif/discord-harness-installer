# Discord 봇 프로비저닝

Developer Portal에서 앱을 만들고, Intent를 켜고, 초대 URL을 만들어 서버에 넣고, 담당 채널에 접근 권한을 주는 것까지가 이 스킬의 범위다. 토큰 발급과 실제 봇 실행은 사용자 몫이다.

이 절차는 **되돌리기 번거로운 실물 변경**(앱 생성, 서버 초대, 채널 권한)을 연달아 일으킨다. 그래서 착수 전 확인표 한 번, 단계마다 실물 재조회 한 번이 이 스킬의 뼈대다.

## 사전 준비 — 사용자가 한다(설치기는 대신 해 주지 않는다)

이 스킬은 **chrome-devtools MCP**가 붙어 있어야 돈다. 제공자는 무관하다 — AgentLayer의 에이전트 브라우저든, 아래처럼 직접 등록한 범용 `chrome-devtools-mcp`든 도구 이름이 같다. 전제는 Node.js(npx)와 크롬, 그리고 화면이 있는 데스크톱이다.

```bash
claude mcp add chrome-devtools -- npx -y chrome-devtools-mcp@latest   # Claude Code
codex  mcp add chrome-devtools -- npx -y chrome-devtools-mcp@latest   # Codex
agy    mcp add chrome-devtools -- npx -y chrome-devtools-mcp@latest   # Antigravity CLI(gemini)
```

- 첫 실행 때 크롬이 **별도 프로필**로 뜬다(`~/.cache/chrome-devtools-mcp/`). 그 창에서 디스코드에 한 번 로그인하면 이후 유지된다. 실사용 크롬의 로그인은 옮겨오지 않는다.
- **등록이 안 됐거나 브라우저 제어가 안 되면 이 스킬을 쓰지 않는다.** 그때는 configure-harness §3 / configure-bot §4의 수동 절차가 정본이다. "완료"라고 하지 말고 그리로 안내한다.
- 봇이 도는 곳이 컨테이너·VPS처럼 화면이 없는 호스트면, 포탈 작업은 **데스크톱에서 이 스킬로 하고** 9단계의 ID 블록만 그 호스트의 `pair` 명령에 넘긴다. 포탈 작업은 웹뿐이라 봇 호스트와 무관하다.

## 모드 두 가지

무엇을 만드는지에 따라 Intent와 스코프가 갈린다. 사용자가 명시하지 않으면 **어느 쪽인지 먼저 묻는다.**

| | **A. 서버 봇** (팀·역할 봇) | **B. 로컬 폴더 봇** |
|---|---|---|
| 쓰임새 | 서버 안에서 멤버·역할을 다루는 봇 — **하네스 4봇**(configure-harness) | 내 폴더에서 돌리는 개인 봇 — **폴더 봇**(configure-bot) |
| Server Members Intent | ✅ 켬 | ❌ 끔 |
| Message Content Intent | ✅ 켬 | ✅ 켬 |
| Presence Intent | ❌ 끔 | ❌ 끔 |
| OAuth2 스코프 | `bot` + `applications.commands` | `bot` 만 |
| 봇 권한 | 아래 8개 동일 | 아래 8개 동일 |
| 서버 초대 | ✅ | ✅ |
| 담당 채널 추가 | ✅ (봇당 여러 채널 가능) | 필요 여부를 확인표에서 묻는다 |

**봇 하나가 채널 여러 개를 담당할 수 있다.** 하네스 4봇이 그 경우다 — 오케스트레이터는 **작업 채널만**, 클로드·코덱스·제미나이 셋은 **작업 + 수다** 둘 다. 확인표에 채널을 나열하고 6.5·7단계를 채널 수만큼 반복한다.

**봇 권한 8개(양쪽 공통)** — 채널 보기 · 메시지 보내기 · 메시지 기록 보기 · 공개 스레드 만들기 · 스레드에서 메시지 보내기 · 링크 임베드 · 파일 첨부 · 반응 추가.
합산 정수 **`309237763136`**. 생성된 URL의 `permissions=` 값이 이것과 다르면 체크가 빠졌거나 더 들어간 것이니 멈추고 다시 고른다.

## 1단계 — 착수 전 확인표

변하는 값은 전부 사용자에게 확인받고 시작한다. 서버나 채널을 잘못 짚으면 남의 팀 채널 권한이 바뀌고, 그건 조용히 지나가기 쉬운 사고다.

확인 없이 진행하지 말 것:

- **모드** (A / B)
- **대상 서버명** — 이름이 비슷한 서버가 여럿이면 어느 것인지, 서버 ID까지 짚어 되읽어 준다
- **봇 이름** (여러 개면 전부)
- **담당 채널명** (봇별로, 여러 개면 전부) — **기존 채널인지, 새로 만들 채널인지**까지 같이 확정한다
- 봇마다 소속·역할 설명이 있으면 받아 적되, **앱 설명(Description) 입력은 요청이 있을 때만** 한다

확인표는 이렇게 되읽어 주고 승인을 받는다:

```
모드: A(서버 봇)
서버: Hermes (1537465993876471859)
  1) tech-qa          → #기술검증팀 (1547782467300229211)
  2) channel-analyst  → #채널그로스팀 (1547782658778734813)

하네스 4봇이면:
  1) orch-bot    → #작업 (…)
  2) claude-bot  → #작업 (…), #수다 (…)
  3) codex-bot   → #작업 (…), #수다 (…)
  4) gemini-bot  → #작업 (…), #수다 (…)
Intent: Server Members ✅ / Message Content ✅ / Presence ❌
스코프: bot + applications.commands / 권한 309237763136 (8개)
```

**서버·채널 ID는 추측하지 말고 실물에서 읽어온다.** 읽는 법은 `references/browser-recipes.md`의 「서버·채널 ID 수집」.

**서버가 모호하면 거기서 멈추고 묻는다.** 이름이 비슷한 서버가 여럿이면 ID로 확정하기 전에 진행하지 않는다.

### 담당 채널이 없을 때

없다고 멈추지 말고 **만들어서 쓴다.** 다만 채널 생성도 실물 변경이라 확인표에 올린다:

- **채널명은 사용자에게 받는다.** 봇 이름에서 임의로 지어내지 말 것 — 서버의 채널 작명 규칙은 사용자만 안다.
- **기본은 비공개 채널**이다. 담당 봇만 들어가는 전용 채널이 이 스킬의 기본 전제이므로, 공개로 만들어야 할 이유를 사용자가 말하지 않는 한 비공개로 만든다.
- 어느 **카테고리** 아래에 둘지 확인한다. 기존 팀 채널들이 모여 있는 카테고리가 있으면 그곳을 제안한다.
- 이름이 비슷한 채널이 이미 있으면 **만들기 전에 되묻는다.** 중복 채널은 사용자가 나중에 혼동한다.

확인표에는 이렇게 구분해 적는다:

```
  1) folder-bot → #folder-bot (신규 생성 · 비공개 · 카테고리: 채팅 채널)
  2) tech-qa    → #기술검증팀 (기존 1547782467300229211)
```

## 2단계 — 사전 점검

1. **브라우저 연결** — `mcp__chrome-devtools__list_pages`가 응답하는지 본다. 도구가 없거나 실패하면 **여기서 멈추고** 「사전 준비」의 등록 명령과 수동 절차를 안내한다. 응답하면 내 탭을 `new_page`로 만들고 남의 탭은 건드리지 않는다(AgentLayer 에이전트 브라우저면 `agent-browser` 스킬 규칙과 동일).
2. **포털 로그인** — `https://discord.com/developers/applications`가 로그인 화면이면 **사용자에게 직접 로그인을 요청한다.** 디스코드 인증은 쿠키가 아니라 localStorage 토큰이라 `cookies import`로 해결되지 않는다. 괜히 시도해서 시간 쓰지 말 것.
3. **중복 검사** — 만들려는 이름이 이미 있는지 두 곳에서 본다. ㉠포털 앱 목록 ㉡대상 서버 멤버 목록. 있으면 **새로 만들지 말고 기존 것의 상태를 확인해 보고한다.**
4. **건드리지 않을 것 목록** — 기존 봇·역할·`@everyone`·카테고리 동기화 상태는 손대지 않는다. 특히 채널 권한 화면의 **「지금 동기화하기」는 절대 누르지 않는다**(기존 개별 권한이 통째로 날아간다).

## 3단계 — 앱과 봇 생성

포털 앱 목록 → `신규 애플리케이션` → 이름 입력 → **개발자 이용약관 동의 체크** → `만들기`.

약관 체크는 앱 생성에 필수라 생성 지시에 포함된 것으로 본다. 다만 완료 보고에 「약관 동의 체크함」을 남겨 사용자가 알게 한다.

생성되면 URL이 `/applications/<APP_ID>/information`으로 바뀐다. **여기서 APP_ID를 받아 적는다.**

### CAPTCHA — 자동 감지 후 자동 재개

생성 버튼을 누르면 hCaptcha(「잠깐! 로봇 아니고 사람 맞죠?」)가 뜰 수 있다. 첫 앱에서 자주 뜨고 이후엔 잘 안 뜬다.

**CAPTCHA는 대신 풀지 않는다.** 사용자가 옆에서 보고 있다거나 눌러 달라고 해도 마찬가지다 — 봇 검증 우회라 예외가 없다. 대신 사람 손을 클릭 한 번으로 줄이고, 그 뒤는 스스로 이어간다:

1. `select_page(pageId, bringToFront: true)`로 탭을 앞으로 띄운다 — **터미널 세션에서는 이게 실질적인 호출 신호다.** 턴 도중에는 사용자에게 말을 걸 수 없고, 말을 하려면 턴을 끝내야 하므로, 탭을 띄워 두고 바로 다음 단계로 간다.
2. **URL이 `/applications/<숫자>/`로 바뀔 때까지 폴링한다** — `references/browser-recipes.md`의 「CAPTCHA 대기」 스니펫. 사용자가 "됐어"라고 말해 줄 때까지 기다리지 말 것. 화면을 보고 있으면 대개 폴링 한 번(약 25초) 안에 잡힌다.
3. 폴링을 6~7회(약 3분) 돌려도 안 풀리면 그때 멈추고 말로 요청한다 — 자리에 없는 경우다.

## 4단계 — Intent

`/applications/<APP_ID>/bot`으로 이동. 모드표대로 스위치를 켜고 `변경 사항 저장`.

두 가지가 발목을 잡는다:

- **스위치를 `click` 도구로 못 누른다.** Discord의 체크박스·스위치는 실제 `input`이 숨겨져 있어 `mcp__chrome-devtools__click`과 `fill`이 "did not become interactive"로 실패한다. `evaluate_script`로 `input.closest('label').click()`을 쓴다(레시피 참조).
- **저장 배너가 사라진 것만으로 저장을 단정하지 않는다.** `변경 사항 저장`을 누른 뒤 **페이지를 새로 불러와 Intent 3개를 다시 읽어** 확인한다. 이게 사용자가 실제로 의심했던 지점이다.

토큰 영역은 읽지도, 찍지도, 초기화하지도 않는다. `토큰 초기화` 버튼 근처를 클릭하지 말 것.

## 5단계 — 초대 URL

**OAuth2 탭의 URL Generator를 쓴다.** `/applications/<APP_ID>/oauth2`

설치(Installation) 탭이 아니다. 설치 탭은 "앱 추가" 흐름의 기본값을 정하는 별개 설정이고, 초대 링크를 만드는 곳이 아니다. 지시가 "설치/초대 링크 구성"이라고 적혀 있어도 실제로 필요한 건 OAuth2 URL Generator다.

1. 스코프 체크 — 모드 A는 `bot` + `applications.commands`, 모드 B는 `bot`만
2. `bot`을 켜면 아래에 봇 권한 목록이 나타난다 — 8개를 체크
3. **생성된 URL의 `permissions=` 값이 `309237763136`인지 확인** (모드 무관 동일)

결과 형태:
```
https://discord.com/oauth2/authorize?client_id=<APP_ID>&permissions=309237763136&integration_type=0&scope=bot+applications.commands
```
모드 B는 끝이 `&scope=bot`이다.

## 6단계 — 서버 초대

생성된 URL로 이동한다. 여기서 두 번 걸린다:

- **「Discord 앱을 여는 중」에서 멈춘다.** 데스크톱 앱으로 넘기려는 화면이다. 잠시 뒤 나타나는 **「Discord로 계속하기」**를 눌러 웹으로 진행한다. 새 탭에서 바로 열면 이 버튼이 안 나오기도 하니, **디스코드 웹이 이미 떠 있던 탭을 그 URL로 이동**시키면 잘 뚫린다.
- 승인은 **두 단계**다. ㉠`서버에 추가:` 드롭다운이 **대상 서버**인지 확인하고 `계속하기` ㉡표시된 권한이 8개인지 확인하고 `승인`.

「성공! <봇>이(가) 승인되어 <서버>에 추가되었어요」를 확인하고 다음으로 넘어간다.

## 6.5단계 — 담당 채널 만들기 (신규일 때만)

확인표에서 "신규 생성"으로 정해진 채널만 만든다. 기존 채널이면 이 단계를 건너뛴다. 봇당 채널이 여럿이면 6.5·7단계를 **채널마다** 반복한다.

대상 카테고리 헤더의 `+`(채널 만들기) → 유형 `텍스트`(기본 선택됨) → 이름 입력 → **`비공개 채널` 스위치를 켠다** → `다음` → 멤버 선택 → `채널 만들기`.

- **비공개 스위치를 켜고 만드는 것이 순서상 안전하다.** 공개로 먼저 만들면 그 짧은 사이 `@everyone`에게 보이고, 나중에 비공개로 돌리면 상태가 지저분해진다.
- **비공개를 켜면 버튼이 `채널 만들기` → `다음`으로 바뀌고 멤버 선택 단계가 붙는다.** 이 화면은 헤더에 **지금 만드는 채널명**이 찍혀 있어 7단계의 채널 혼동 위험이 없다 — **여기서 담당 봇을 바로 넣는 것이 가장 안전하고 빠르다.** 넣었으면 7단계는 검증만 하면 된다.
- 이 단계에서 봇을 안 넣고 `건너뛰기`를 눌렀다면, 7단계를 정석대로 밟는다.
- 만들어진 채널의 **ID를 받아 적는다** — 생성 직후 URL이 `/channels/<GUILD_ID>/<새 CHANNEL_ID>`로 바뀐다.
- 이름이 자동으로 소문자·하이픈으로 바뀐다(`Local Bot Test` → `local-bot-test`). 사용자가 준 이름과 달라지면 **바뀐 이름을 보고한다.**

## 7단계 — 담당 채널 접근 (여기가 제일 조심할 곳)

비공개 채널에 봇을 넣으려면 채널 권한에 **그 봇만의 멤버 항목을 추가**한다. 기존 항목은 건드리지 않는다.

**반드시 이 순서를 지킨다:**

1. **대상 채널을 먼저 연다** — `navigate_page`로 `https://discord.com/channels/<GUILD_ID>/<CHANNEL_ID>`
2. 그 채널의 `채널 편집`을 열고 `권한` 탭으로 간다
3. `멤버 또는 역할 추가`를 누른다
4. **모달 상단의 채널명이 대상 채널인지 눈으로 확인한다** ← 이 확인을 거르지 말 것
5. 목록에서 **`앱` 항목**을 고른다(같은 이름의 `역할` 항목이 따로 있다 — 역할이 아니라 앱이다)
6. `완료`를 누른다
7. 멤버 목록에 봇이 들어왔는지 다시 읽어 확인한다

### 왜 1번이 중요한가

`멤버 또는 역할 추가` 모달은 **설정 창을 연 채널이 아니라 화면이 보고 있는 채널**에 붙는다. 다른 채널을 보는 상태에서 사이드바로 B채널 설정을 열고 멤버를 추가하면, 봇이 **보고 있던 A채널에 들어간다.** 실제로 이 사고가 났고, 남의 팀 채널에 봇이 붙었다. 4번 확인만 해도 잡힌다.

### 잘못 넣었을 때

당황하지 말고 되돌린다. 해당 항목의 `제거하기` → 확인 대화상자의 `확인`. 그 뒤 그 채널의 멤버 목록을 다시 읽어 원래 구성으로 돌아왔는지 확인하고, **완료 보고에 사고와 복구를 반드시 적는다.** 조용히 덮으면 사용자가 나중에 이상한 상태를 혼자 발견하게 된다.

## 8단계 — 최종 검증

단계마다 봤더라도, 끝에 한 번 더 실물을 읽는다. 중간 확인은 화면 잔상일 수 있다.

디스코드 웹을 **새로 불러온 뒤**:

- 봇별로 담당 채널 권한 화면의 **멤버 목록**을 읽어 해당 봇이 있는지
- 이번에 손댄 적 없는 이웃 채널 하나를 골라 **원래 멤버 구성 그대로인지**(오배치가 있었다면 그 채널을 반드시 포함)
- 포털에서 앱별 Intent를 **재조회**로 한 번 더

## 9단계 — 연결 정보 정리

봇을 실제로 붙이려면 토큰 말고도 **ID 몇 개**가 필요하다. 사용자가 이걸 다시 찾아다니지 않도록, 여기서 모아 붙여넣기 좋은 형태로 만들어 준다.

| 값 | 어디서 얻나 |
|---|---|
| **Application ID** | 앱 생성 직후 URL `/applications/<여기>/` |
| **봇 사용자 ID** | **Application ID와 같다** — 따로 찾을 필요 없다 |
| **서버(길드) ID** | 1단계에서 읽은 값 |
| **채널 ID** | 담당 채널의 ID (신규 생성이면 생성 직후 URL). 하네스는 작업·수다 두 개 |
| **사용자 ID**(운영자 본인) | 아래 방법으로 읽는다 |

「봇 사용자 ID = Application ID」는 서버에 있는 봇 8개에서 아바타 URL의 ID와 포털 Application ID를 대조해 확인한 것이다.

**사용자 ID 읽기** — 디스코드 웹에서 아바타 이미지 URL의 숫자가 곧 사용자 ID다. 개발자 모드를 켜거나 우클릭할 필요 없다. `references/browser-recipes.md`의 「사용자 ID 읽기」 참조. 기본 아바타를 쓰는 계정은 URL에 ID가 없으니, 그때는 사용자에게 **디스코드 설정 → 고급 → 개발자 모드**를 켜고 자기 이름 우클릭 → `사용자 ID 복사`를 부탁한다.

## 완료 보고

표 하나로 정리한다. 봇마다:

- 봇 이름 / 사용자명(`name#1234`)
- Application ID
- Developer Portal URL
- 대상 서버명·ID, 담당 채널명·ID
- Intent 설정(Server Members / Message Content / Presence) — 모드에 맞는지
- 초대 URL과 `permissions` 값
- 서버 초대 확인 / 채널 권한 확인

그리고 **붙여넣기 좋은 연결 정보 블록**을 봇마다 하나씩 낸다. 사용자가 설정 파일로 그대로 옮길 수 있어야 한다:

```
# tech-qa
DISCORD_APPLICATION_ID=1548132634201161768   # 봇 사용자 ID와 동일
DISCORD_GUILD_ID=1537465993876471859         # Hermes
DISCORD_CHANNEL_ID=1547782467300229211       # #기술검증팀
DISCORD_OWNER_USER_ID=1062698028051472516    # netwaif
DISCORD_BOT_TOKEN=                           # ← 여기만 직접 채우세요
```

설치기·폴더 봇으로 이어가면 이 값이 그대로 들어간다: `DISCORD_CHANNEL_ID` → `pair --channel-id`, `DISCORD_OWNER_USER_ID` → `pair --user-id`(사람 계정 ID — 봇 ID 아님), 토큰은 `.bot-token` 파일로(채팅에 붙여넣지 않는다 — 각 스킬의 토큰 절 참조).

변수 이름은 사용자의 봇이 쓰는 이름에 맞춘다. 어떤 이름을 쓰는지 모르면 위 형태로 주고 **"쓰시는 설정 파일 키 이름에 맞춰 바꿔 넣으세요"**라고 한 줄 덧붙인다. 토큰 줄은 **비워서** 내보내되 자리는 남겨 둔다 — 어디를 채워야 하는지가 한눈에 보인다.

표 아래에 반드시 덧붙일 것:

- **토큰 안내** — 표시·복사·저장·Reset 모두 하지 않았음을 밝히고, 사용자가 **작업이 다 끝난 뒤** 각 앱 Bot 탭에서 `토큰 초기화`를 눌러 나온 값을 위 블록의 빈칸에 넣어야 봇이 붙는다는 것(그 전까지는 오프라인)
- **사람 확인이 필요했던 지점** — CAPTCHA, 로그인, 약관 동의 체크
- **미완료·판단 보류 항목** — 앱 설명을 안 넣었다면 그 사실
- **사고가 있었다면 사고와 복구 전말**

## 안전 경계

- CAPTCHA·MFA·로그인은 사람이 한다. 우회하지 않는다.
- 토큰·비밀번호·복구 코드는 표시·복사·저장·전송하지 않고, 그것이 보이는 스크린샷도 남기지 않는다.
- 기존 앱 삭제, 유료 결제, 계정 설정 변경은 하지 않는다.
- 기존 봇·역할·`@everyone` 권한과 카테고리 동기화 상태는 바꾸지 않는다. `지금 동기화하기` 금지.
- 봇 코드·`.env`·게이트웨이·CLI 설정은 이 스킬의 범위 밖이다. 요청이 있으면 별도로 확인받고 한다.
- 브라우저 제어가 안 되면 "완료"라고 하지 말고 필요한 연결 방법을 알린다.
